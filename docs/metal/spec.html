Mirin Metal Runtime

Status: Draft for owner review Date: 2026-10-29 Scope: Linux first (Fedora/KDE Wayland) Related: docs/metal.md, docs/architecture.md, docs/api-design.md

1. Summary

Metal today renders React through GPUI from a standalone, single-window stdio host. That proved the renderer. This spec turns it into a runtime: a Metal app is a real mirin app, with the same mirin.config.ts, the same mirinjs main-process APIs, the same typed RPC, and the same mirin dev / check / build / release loop. Only the UI layer differs: Metal components instead of a webview.

The runtime has four parts:

  • A native library, libmirin_metal, loaded in-process through Bun FFI. It owns the main thread and runs GPUI.
  • Two Bun Workers per app: the App Worker runs src/main.ts exactly as on CEF; the UI Worker runs React and every window's component tree.
  • A retained-tree UI protocol with patches instead of whole-tree JSON, and an event channel that wakes Workers instead of polling them.
  • Desktop integration aimed at the desktop environment Metal is meant to power: app identity, session theming, multiple windows, and shell surfaces (panels, docks, overlays).

2. Context and constraints

Where Metal is today

Constraints this spec must honor

  • The mirinjs contract (owner rule). Metal implements the shared app surface and may not break, fork, or shadow any mirinjs export, event, config key, or RPC frame. Metal-only surface lives in @mirinjs/metal. Shared additions go through docs/api-design.md sign-off.
  • Main thread. GPUI, like CEF, needs the process main thread. A process is either a CEF app or a Metal app, never both.
  • Threading rules from docs/architecture.md §2. UI work happens on the main thread; Workers only enqueue commands; no thread blocks on another.
  • Flat C ABI, thin ffi.rs, JSON envelopes (docs/conventions.md).
  • A desktop environment, not one app. Many resident apps run at once, so idle cost, memory, and startup are first-class requirements (§16).

3. Goals and non-goals

Goals

  • A Metal app's mirin.config.ts and src/main.ts run unchanged against the CEF flavor, apart from the window UI declaration.
  • In-process FFI host with no stdio hop; Workers isolated from the UI thread.
  • Typed RPC between main-process code and UI, with no network listener.
  • Multiple windows per app, plus shell surfaces for the desktop's shell.
  • Keyboard, focus, and clipboard good enough to port Anko 1:1.
  • Full tooling: mirin dev, check, doctor, build, release, Linux packages without a CEF download.
  • Zero idle wakeups and a per-app memory budget.

Non-goals for v1

  • macOS and Windows Metal. GPUI supports them; the runtime is designed not to preclude them, but v1 ships Linux.
  • Mixing a CEF webview and Metal UI in one process. A hybrid app would need a second process; not in v1.
  • Accessibility (AT-SPI). Planned through AccessKit after v1; the node protocol reserves roles and labels now.
  • Animations and transforms. Separate renderer work.
  • A native code editor. Needed for Anko's SQL editor, specified separately.

4. Process and thread model

One OS process per app, mirroring the CEF flavor's host/Worker split:

ThreadOwnsNever does
MainGPUI app and windows, Wayland connection, GPU, retained UI trees, platform calls that must be on the UI thread.Run JavaScript; block on a Worker.
App WorkerThe user's src/main.ts; all mirinjs main-process APIs; the RPC router.Render UI; touch GPUI directly.
UI WorkerReact reconciliation for every window; event handlers; mirinjs/client.Call privileged main-process APIs except through RPC (same boundary as a webview).
Rust internalEvent notification, file dialogs (portal), image decoding.Touch GPUI state outside the main thread.

Proposed: one UI Worker per app, not one per window. A JSC VM costs roughly 10–20 MB. Per-window Workers would isolate windows from each other, but a desktop runs dozens of apps, and windows of one app share state and components. Apps that need isolation can still split heavy work into extra Workers (workers in the manifest).

Boot sequence

  1. The host resolves paths, reads the manifest, and dlopens libmirin_metal.
  2. It calls mirin_metal_prepare(config): GPU driver selection (already in gpu.rs), single-instance check, event pipes. This must happen before any thread starts.
  3. It spawns the App Worker and the UI Worker, handing each its event pipe and a MessagePort pair for RPC.
  4. It calls mirin_metal_run() on the main thread, which never returns until quit.
  5. Declared windows open; each gets a root in the UI Worker, which mounts the window's component; ready fires in the App Worker once every auto-open window has painted its first frame.

5. Native library

libmirin_metal is a new cdylib built from crates/mirin-metal, separate from libmirin_core so the CEF core never pulls in GPUI and Metal apps never download CEF. Platform features both flavors need move into a shared crate: 

crates/
  mirin-core/        CEF flavor (cdylib): CEF browser process, CEF windows
  mirin-metal/       Metal flavor (cdylib + host bin): GPUI windows, UI trees
  mirin-platform/    NEW, no CEF and no GPUI: dialogs (portal), clipboard,
                     notifications, global shortcuts, tray, single instance,
                     app identity, session settings (theme, fonts)
  mirin-codec/       updater codec (unchanged)

C ABI (v1)

Same conventions as libmirin_core: flat C functions, JSON options, handles allocated synchronously, work posted to the main thread, no panics across FFI.

// lifecycle (host only)
mirin_metal_prepare(config_json) -> i32          // before any thread starts
mirin_metal_run() -> i32                          // owns the main thread until quit
mirin_metal_event_fd(worker: u8) -> i32           // notify pipe read end per Worker
mirin_metal_poll_event(worker: u8) -> *char       // drain one JSON event or null

// windows (App Worker)
mirin_metal_window_create(opts_json) -> u32      // returns window id
mirin_metal_window_close(id)
mirin_metal_window_control(id, cmd_json)          // minimize, maximize, focus, show, hide, …
mirin_metal_window_set_title(id, title)
mirin_metal_app_quit()

// UI trees (UI Worker)
mirin_metal_commit(window, batch_ptr, len) -> i32 // apply a patch batch (§7); 0 = ok
mirin_metal_query(window, query_json) -> *char    // layout / focus / hit-test queries
mirin_metal_sim(window, command_json)             // dev only: simulated input

// platform features (App Worker), shared with libmirin_core via mirin-platform
mirin_metal_dialog_show(opts_json)
mirin_metal_clipboard_read_text() -> *char
mirin_metal_clipboard_write_text(text)
mirin_metal_notification_show(opts_json) -> i32
mirin_metal_shortcut_register(id, accelerator) -> i32
mirin_metal_shortcut_unregister(id)
mirin_metal_tray_create(opts_json)
mirin_metal_tray_destroy(id)

The mirinjs Worker code selects a binding table by flavor (native.ts for CEF, a Metal equivalent with the same TypeScript interface). Feature modules (dialog.ts, clipboard.ts, …) stay byte-for-byte shared.

6. Commands and events

Commands (Worker → Rust)

Every exported function is callable from either Worker thread. It validates its input, pushes a command onto a lock-free queue, and wakes the GPUI loop through the async channel already used by the alpha (window.rs). Commands that return data (query, clipboard reads) are answered from main-thread state snapshotted after each frame, so they never wait on the main thread.

Events (Rust → Worker)

The CEF flavor polls mirin_poll_event every 8 ms, because a bun:ffi callback fired from the blocked main thread never reaches a Worker's loop. That costs 125 wakeups per second per app forever, which a desktop cannot afford. Metal instead pairs each queue with a pipe:

  1. Rust pushes the event onto that Worker's queue and, if the queue was empty, writes one byte to the Worker's notify pipe.
  2. The Worker awaits a read on the pipe's read end (a Bun stream over the file descriptor), then drains the queue through mirin_metal_poll_event until it returns null.
  3. Idle apps make no wakeups at all.

Fallback. If Bun cannot await a pipe reliably inside a Worker, poll with back-off: 4 ms while events flowed in the last 250 ms, then doubling to 250 ms. The event envelope is unchanged either way, so the transport can switch without touching callers.

Event envelope, same as architecture.md §3:

{ "v": 1, "kind": "event", "type": "ui.press", "target": 3, "payload": { "node": 812, "x": 410, "y": 96 } }

7. UI protocol v2: retained trees and patches

Today every React commit serializes the whole tree (89 KB for the example browser) and Rust replaces its tree. v2 keeps the tree in Rust and sends only what changed, which the reconciler already knows from its mutation methods.

Patch batch

{
  "v": 2,
  "ops": [
    ["create", 812, "view", { "direction": "row", "gap": 8, "onPress": true }],
    ["create", 813, "text", { "size": 14 }, "Save"],
    ["append", 812, 813],
    ["insert", 40, 812, 77],                 // parent, child, before
    ["update", 377, { "background": "#262626" }, ["hoverBackground"]],  // set, unset
    ["text", 813, "Saved"],
    ["remove", 40, 655],                      // detaches and frees the subtree
    ["root", 40]
  ]
}
  • Node ids are allocated by the UI Worker (reconciler instance ids) and are unique per window.
  • A batch is atomic: the renderer applies it between frames and never paints a half-applied commit.
  • Props use the existing v1 node vocabulary (docs/metal.md §2), parsed strictly at the boundary. Unknown ops or props reject the whole batch with an error event, never a partial tree.
  • Virtualized lists, input state, scroll state, and layout caches key off node ids, so updates no longer rediscover them by walking the tree.
  • The v1 whole-tree form stays as ["replace", tree] for the stdio host and debugging.

Encoding

JSON first, behind the length-prefixed mirin_metal_commit(ptr, len) call so the encoding can move to a binary form later without an ABI change. Benchmarks decide that (§16).

Events from the tree

Interaction events carry the node id and its painted bounds, as today. New: ui.key (§12), ui.focus, ui.layout for subscribed nodes, and ui.frame for requestAnimationFrame.

8. RPC between workers

The typed RPC router from api-design.md §3 works unchanged. Only the transport differs: where a CEF webview connects to a token-authenticated loopback WebSocket, the Metal UI Worker talks to the App Worker over a MessagePort pair the host creates at boot. 

// src/rpc.ts — shared, unchanged
export const router = rpc.router({
  runQuery: rpc.mutation(async (sql: string, ctx) => db.run(sql)),
  progress: rpc.event<{ pct: number }>(),
});

// src/windows/main.tsx — Metal UI, same client API as a webview
import { client } from "mirinjs/client";
const api = client<Router>();
const rows = await api.runQuery("select 1");
  • mirinjs/client selects the in-process transport when it runs in a Metal UI Worker; no code change for the app.
  • ctx.window is the handle of the window whose root issued the call; the UI Worker tags each call with its window id.
  • app.windows.get(name).rpc.x.emit() and app.rpc.x.broadcast() deliver to the matching roots.
  • No network listener exists, so the token and the accepted loopback-sniffing gap from the CEF flavor do not apply.

10. Configuration

needs owner sign-off These are additions to the shared mirinjs/config surface, so they go through docs/api-design.md. They are additive and ignored or rejected clearly on the CEF flavor.

export default defineConfig({
  id: "dev.netko.anko",
  name: "Anko",
  engine: "metal",                      // NEW: "cef" (default) | "metal"

  windows: {
    main: {
      title: "Anko",
      width: 1280,
      height: 820,
      view: "src/windows/main.tsx",     // NEW, Metal: module whose default export is the window's component
      // url: "app://ui/index.html",    // CEF only; an error with engine: "metal"
    },
    panel: {
      view: "src/windows/panel.tsx",
      surface: {                        // NEW, Metal + Wayland: a shell surface (§11)
        layer: "top",
        anchor: ["top", "left", "right"],
        exclusiveZone: 36,
        keyboard: "on-demand",
      },
    },
  },
});
  • engine picks the flavor at build time; the CLI then packages libmirin_metal instead of CEF.
  • view is the Metal counterpart of url. Exactly one of them is valid per engine; the other is a config error naming the right key.
  • Every other key keeps its meaning. cef.* is ignored on Metal with a warning.

A window component receives its handle through a hook, so UI code never imports main-process modules:

// src/windows/main.tsx
import { useWindow } from "@mirinjs/metal";
export default function Main() {
  const window = useWindow();          // name, id, controls (proxied through RPC)
  return <App onClose={() => window.close()} />;
}

11. Windows and shell surfaces

Regular windows

GPUI windows, multiple per app. Client-side or server-side decorations follow the compositor; KWin provides server-side ones. The title is set explicitly after creation (GPUI's Wayland backend ignores it otherwise).

Shell surfaces

The desktop's shell (panel, dock, launcher, notifications, lock screen, OSD) needs Wayland wlr-layer-shell surfaces: anchored to screen edges, optionally reserving space (exclusive zone), on a stacking layer, with controlled keyboard focus. GPUI does not create them, so this goes into mirin's GPUI fork as a new window kind.

OptionValuesMeaning
layerbackground | bottom | top | overlayStacking layer.
anchoredgesWhich screen edges the surface attaches to.
exclusiveZonepxSpace other windows avoid (a panel's height).
keyboardnone | on-demand | exclusiveKeyboard focus policy (a launcher is exclusive).
outputmonitor name, or allWhich monitor; one surface per monitor when "all".

Popups (menus, tooltips, selects) become real xdg_popup surfaces when they would overflow the window, instead of being clipped to it as today.

13. Web API shims

Porting web-built apps (Anko first) needs a few browser globals in the UI Worker. They are an explicit opt-in import, @mirinjs/metal/web, so plain Metal apps do not carry them:

Anything outside this list stays undefined, so a dependency that needs the DOM fails loudly instead of misbehaving.

15. Desktop integration

  • App identity. The manifest id becomes the Wayland app_id and the .desktop file name, so taskbars group windows and show the right icon.
  • Activation and single instance. A second launch hands its arguments and xdg-activation token to the running instance over D-Bus, which raises the window and emits open-url when relevant.
  • Session theme. Color scheme, accent color, and contrast come from the XDG settings portal; metal-ui's ThemeProvider follows them by default and updates live.
  • Fonts. The UI and monospace families come from fontconfig, as now, with a session override.
  • GPU. Load only the compositor's GPU driver (implemented: dmabuf feedback, gpu.rs).
  • Portals. File dialogs, notifications, and opening URIs through XDG portals, so apps work sandboxed (Flatpak) without changes.
  • Inter-app communication. Out of scope for v1; the shell will need it (D-Bus services exposed from the App Worker), tracked as follow-up.

17. Security

  • The UI Worker has the same privilege boundary as a webview: privileged APIs only through RPC handlers in the App Worker.
  • No network listener: RPC and devtools for Metal use MessagePorts and the existing token-authenticated inspector only in development.
  • Every FFI input is validated at the boundary (strict serde, length checks); a malformed batch is rejected whole.
  • The simulation channel and renderer capture are compiled in but refuse to run in packaged builds unless devtools.production is set.
  • Images load from local paths only; the UI Worker fetches and caches remote images, never the renderer.

18. Milestones

Each milestone lands as working software with its acceptance checks green, docs updated in the same change, and budgets intact.

R1 · In-process core

  • libmirin_metal cdylib and host bootstrap (mirin_metal_prepare/run), single window, UI in a Worker, notify-pipe events, commands queued to the GPUI loop.
  • Accept: the example browser runs in-process; benchmark at or below the stdio host; idle wakeups 0; existing headless and sim tests pass over FFI.

R2 · Two Workers, RPC, windows

  • App Worker running src/main.ts; UI Worker with one root per window; MessagePort RPC; app lifecycle and app.windows; useWindow(); engine and view config (after sign-off).
  • Accept: examples/hello-metal with a typed RPC call and two windows; unchanged mirinjs unit tests.

R3 · Retained trees and patches

  • Reconciler emits patch batches; Rust keeps per-window trees; virtualized lists, inputs, and scroll state keyed by node id.
  • Accept: patch and byte budgets met; example browser and all metal-ui tests pass.

R4 · Platform features

  • Extract mirin-platform; dialogs, clipboard, notifications, global shortcuts, tray on Linux for both flavors; rendered menu.popup.
  • Accept: a Metal kitchen-sink exercises each API; the CEF flavor's Linux behavior is unchanged.

R5 · Input and web shims

  • Key events, focus model, keyboard navigation in metal-ui overlays, text selection and copy, IME, @mirinjs/metal/web.
  • Accept: metal-ui menus, selects, dialogs, and command palette usable by keyboard alone; Anko's shortcuts work.

R6 · Tooling and packaging

  • mirin dev/check/doctor/build/release for engine: "metal"; renderer capture; native package.
  • Accept: Anko's Metal app builds an rpm with mirin build and passes mirin check off-screen.

R7 · Desktop integration and shell surfaces

  • App identity, activation, session theme, portals; layer-shell surfaces and xdg_popup overlays in the GPUI fork; multi-monitor.
  • Accept: an example top panel with an exclusive zone and a launcher overlay under KWin; theme follows a live color-scheme switch.

20. Risks

  • GPUI on a Bun-created main thread. The stdio host avoided this; R1 must prove GPUI initializes and runs its loop on the thread the Bun host hands over (the CEF flavor proved the same for CEF).
  • Awaiting a pipe from a Worker. If Bun's fd streams misbehave in Workers, the back-off poller covers it at some idle cost.
  • Fork maintenance. Layer-shell and grid changes grow the GPUI diff; rebasing onto new GPUI releases costs time. Mitigation: small, documented patches; upstream what is generic.
  • Two JS VMs per app. Memory per app rises by one VM. Mitigation: budget enforced in CI; shared-VM mode for tiny shell applets if needed.
  • Keyboard handling round trip. Default actions waiting on the UI Worker could add latency; the same-frame deadline keeps typing local.

Mirin Metal: Desktop Shell Plan

Status: Plan for owner review Date: 2026-10-29 Builds on: docs/metal/spec.html (runtime, decisions accepted)

1. Short answer

The runtime spec already anticipates the shell (layer-shell surfaces in milestone R7), but only as one feature. A shell needs more: a compositor strategy, system services, a privilege model, and a way to host third-party applets. The architecture does not need to change in its foundations: process-per-app, GPUI as a Wayland client, the Worker split, the patch protocol, and the mirinjs contract all hold. It needs seven extension points (§5), and two of them should shape R1–R7 now so the shell does not force a redesign later.

Recommendation. Build the shell as privileged Metal apps that are Wayland clients of a compositor, depending only on standard protocols. Develop it on KWin in a nested session, validate it on a second compositor, and decide on a mirin-owned compositor (Rust, Smithay) at a checkpoint once the shell shows where an existing compositor holds it back. This is the architecture System76's COSMIC ships: a Smithay compositor, shell components as layer-shell clients, and apps on its own toolkit.

OptionGainsCosts
A. Shell as clients of KWinMature, already on the owner's machine, supports layer-shell; zero compositor work.KWin's window management, effects, and Plasma-specific protocols; a Plasma flavor to the session; KWin release cadence.
B. Shell as clients of a wlroots compositor (labwc, sway)Standard wlr/ext protocols, lightweight, easy to configure.Window management and animations are someone else's design; C, not Rust.
C. Own compositor on Smithay (mirin-comp)Full control of window management, animations, gestures, and protocols; Rust, same stack as Metal; COSMIC and niri prove the path.A large, long-lived project: input devices, outputs, XWayland, screencast, accessibility, stability.
D. Shell inside the compositor (GNOME Shell model)Tight integration, compositor-drawn UI.GPUI is a client toolkit, not a compositor renderer; one crash takes everything down.

Plan: A for development, with B as a portability check, so the shell only uses standard protocols. C decided at checkpoint S3 with evidence. D is ruled out.

4. The shell as a Metal app

The shell is not a new kind of program. It is a Metal app with privileged capabilities and shell surfaces, built with the same runtime as any app:

ProcessSurfacesWhy separate
mirin-shellPanel and dock per monitor, launcher, notification toasts and center, OSD, quick settings, app switcherOne process for memory: one GPUI, two Workers, many surfaces. Restarted by the session on crash.
mirin-lockLock surfaces on every outputMust stay up when the shell crashes; minimal code; the compositor keeps the session locked if it dies.
mirin-greeterLogin screen (under greetd)Runs before any user session exists.
mirin-settings, appsNormal windowsOrdinary apps; no shell privileges.
mirin-servicesNoneSession services and the portal backend (E4, E6); no UI, so a UI crash never takes audio or notifications down.

5. Architecture changes

None replace the runtime spec; all extend it. E1 and E3 should be designed into R1–R7 now.

E1 · Surface roles and outputs shape R7 now

  • Window kinds beyond toplevels: layer surfaces, popup surfaces (positioned against an anchor, flipping at screen edges), lock surfaces (ext-session-lock), each a GPUI fork addition.
  • Output lifecycle: monitors added, removed, rescaled, rearranged reach the App Worker as events; a surface can be declared per output (output: "all") and is created and destroyed with its monitor.
  • The UI root receives its surface's role and output so a panel renders per monitor.

E2 · UI contexts and slots S2

  • Apps keep one UI Worker (accepted). The shell can add UI contexts: extra UI Workers for applets and extensions, each with its own permissions.
  • A slot node in one context's tree hosts another context's root, so a third-party applet renders inside the panel without access to the panel's tree or APIs.
  • Node ids are namespaced per context in the patch protocol. Reserve the namespace field in protocol v2 now, even before contexts exist.

E3 · Capabilities shape R2 now

  • Privileged surfaces and APIs are capabilities declared in the manifest and granted by the session, never assumed: shell.surface, shell.toplevels, shell.workspaces, session.lock, services.*.
  • The compositor enforces protocol access (a security-context allowlist on KWin or wlroots, built in on a mirin compositor); the runtime enforces API access in the App Worker.
  • An ordinary app declaring surface without the grant fails at startup with a clear error. R2's config validation should already route through a capability check, even if it grants everything during development.

E4 · System services S2

  • A D-Bus layer in Rust (zbus) in mirin-platform, event-driven, exposed to Workers through a typed package, @mirinjs/shell.
  • Services: open windows and taskbar actions, workspaces, notifications server, tray host (StatusNotifierItem), media (MPRIS), audio (PipeWire), network (NetworkManager), power and sessions (UPower, logind), Bluetooth (BlueZ), polkit agent, idle and inhibition.
  • Long-running services live in mirin-services; the shell subscribes over RPC, so UI restarts never drop state.

E5 · Session supervision S1

  • Each shell process is a systemd user unit with readiness notification and restart on failure; the session target orders them.
  • The shell persists its state (open launcher query, notification history) so a restart is invisible.

E6 · Design tokens as a session service S2

  • mirin-services implements the XDG settings portal (color scheme, accent, contrast) plus mirin tokens (radius, fonts, density) and pushes changes live.
  • metal-ui's ThemeProvider follows the session by default; CEF apps get the same values through CSS variables.

E7 · Always-resident performance ongoing

  • Shell budgets stricter than apps: zero idle CPU and wakeups, panel memory under a fixed ceiling, input to frame within one frame.
  • Later: a pre-forked runtime template to cut app cold start, and shared glyph and icon caches across processes.

What stays the same

Process-per-app, GPUI as the client toolkit, the Worker split, the patch protocol, the mirinjs contract, and the accepted decisions in the runtime spec.

9. Risks

  • Compositor lock-in. Building against KWin-only protocols would make S3's choice for us; the adapter rule in §6 keeps it open.
  • Scope. A desktop is many projects. The roadmap keeps each phase usable on its own, and S3 is an explicit stop-and-decide point.
  • Shell crash blast radius. Lock screen, services, and greeter are separate processes for this reason; the shell restarts transparently.
  • GPUI fork growth. Surface roles add to the fork; keep each patch small, documented in MIRIN.md, and upstream what is generic.
